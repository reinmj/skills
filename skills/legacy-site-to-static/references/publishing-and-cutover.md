# 发布、旧程序隔离与正式入口

先记录当前项目的域名、解析、边缘代理、源站、FTP 根和公开目录。所有示例值都需替换为核对过的当前项目数据。

## 分层检查，尤其是 503

控制台“已启动”不代表前置代理已放行。按 DNS、CDN/反向代理、源站、文件路径逐层验证：

- 对真实域名请求首页、版本文件和一个静态资源；保存状态、Server、Location 与版本，避免只看首页标题。
- 用正确 Host 直接访问源站；HTTPS 同时需要正确 SNI 和证书验证，可用 `curl --resolve`，不要修改全局 DNS 来做诊断。
- 若源站返回 200，而 ECS Nginx 返回 503，检查匹配域名的 HTTP/HTTPS server 和全局维护规则。`return 503;` 会提前结束请求，文件上传或主机开站不能绕过它。
- 只检查用户指定的站点，不输出无关站点的凭据或完整配置。区分磁盘配置与正在运行的行为；本机带 Host/SNI 的请求可交叉验证。

`probe_routes.py` 发出有限 GET，不跟随重定向、不打印正文或 Cookie；默认启用 TLS 校验。只选择已知的公开展示路径，不遍历管理、删除、注销等接口。它不能检测所有业务功能，也不能证明浏览器渲染完整。

## 预览与正式发布

预览应有页面级 noindex 或已验证的范围限定响应头。子目录里的 robots.txt 不等于整个站点的 robots 策略，避免为预览屏蔽仍在运行的正式站。

正式切换核对：索引策略与用户意图一致、正式域名的 robots.txt 正确、产品及图片路径正确、确认译文数量没有意外回退。未确认译文提示页、删除页可以继续 noindex。用户需要正式站继续禁收录时，在检查配置设 `require_indexing: false`，不要为通过默认检查擅自开放收录。

物理目录可继续使用原预览目录。若它被域名根路径映射，必须在工具中改标为正式目录，并同步操作说明：之后往那里上传就是更新官网。独立预发布需求另建目录，不把已经上线的目录当作不会影响用户的沙箱。

## FTP-only 主机

构建、编辑、翻译与发布程序运行在本地电脑；服务器只存公开静态文件。不要要求云虚拟主机安装 Node 或允许 SSH。

发布流程的关键边界：

1. 保存当前完整编辑资料、不可变发布文件和目标指纹（服务器、账号标识、目录及发布 ID，不含密码）。
2. 测试连接只登录、定位和列目录；不偷偷上传测试首页或变更网站。
3. 核对路径不存在符号链接逃逸、空间和平台目录限制。备份本次将覆盖的远程文件及其原始存在状态。
4. 上传临时文件并回读校验。先准备完，再按资源、页面、首页、版本标记的顺序提交。
5. 可恢复失败按日志还原已替换内容；恢复不完整时保留备份和路径记录，停止该批操作，不继续尝试正式发布。

普通 FTP 的字节传输不加密。主机支持时使用验证证书的 FTPS/SFTP；不静默降级。不支持加密的产品，应说明实际方式并由用户在本地输入账号。FTP 逐文件提交不是全站事务；断电和强退不能宣称必定自动回滚。

本机成功哈希加远程 SIZE 的跳过策略不能证明远端内容没有被等长篡改。来源不明、另一个客户端改过文件或清理入侵后，选择完整上传/回读验证，不把“跳过”说成已逐字节核对。

## 旧程序与平台目录

先列清单和可回退位置，再移动用户网站的旧程序到已核实的非公开位置。移目录通常比下载再上传省带宽；它不是对原漏洞打补丁。对照路径、类型、大小及已实际计算的内容哈希核验，不把目录清单哈希说成全部文件内容哈希。

平台的日志、统计、只读根目录和保留文件必须独立识别。任何顶层项目都不能只因“不是新版目录”就当旧程序迁走。第一次失败时停止本批并恢复已移动的用户文件，核对原位和备份；先找原因，再做新的有界尝试。不强行改平台系统目录权限。

网站开站前确认：旧动态程序已离开可执行的公开路径，新目录的脚本策略生效，平台安全/停权状态允许访问。文件位 0644/0755、站点启停、PHP 版本、禁止脚本执行是不同控制。

阿里云云虚拟主机的条件经验，使用时先核对当前官方文档及实际产品：

- 常见 FTP 根下的 `/htdocs` 是公开网站目录；`/myfolder` 可作为非公开存储，但不能套用到其他平台。
- `htdocs` 中的 `logreport` / `report` 可能是受保护系统项目；保留并核对，不把它们纳入旧站移动。
- 文件管理器里的 `/` 可能只是站点逻辑根。根目录禁脚本选项不可选时，改选实际静态子目录核对权限，不反复开关主机试错。
- 设置目录策略时核对子目录应用与生效结果。以控制台状态及真实静态请求验证，不只看选中的单选按钮。

- [文件和目录权限](https://help.aliyun.com/zh/cloud-web-hosting/user-guide/settings-file-and-directory-permissions)

## Nginx 入口切换

用户授权切换入口后，只改对应域名配置。使用已有授权管理通道；权限不足时先完成可读备份、候选差异与验证方案，不把扩大主机特权当成默认解决方式。

备份存到不被 `include *.conf` 加载的位置，记录 SHA256。保留文件属主、权限、必要属性及其他站点配置。生成精确差异，检查通过后平滑重载，复查实际响应；失败回退本次配置。不要顺带更新其他域名、TLS、DNS 或服务器软件。

在已有的 TLS server 中，整站 URI 映射可采用以下形状。`192.0.2.40` 和 `www.example.invalid` 都是示例；保留当前项目适用的代理头、日志和 TLS 配置：

```nginx
location = /site-release {
    return 301 /;
}
location ^~ /site-release/ {
    rewrite ^/site-release/(.*)$ /$1 permanent;
}
location / {
    proxy_pass http://192.0.2.40/site-release/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_redirect http://192.0.2.40/site-release/ /;
    proxy_redirect http://www.example.invalid/site-release/ /;
}
```

核对尾部斜杠与 URI 替换语义。不能仅把根目录首页设置为某个子目录的 index.html，却不处理其相对图片和页面路径。源站地址不能重新解析回当前代理本身。原预览重定向要保留查询参数，检查嵌套英文和目录补斜杠是否循环、是否泄漏内部前缀。

做候选配置检查时，相对 include 可能相对于候选主配置所在目录解析。使用核对过的绝对 include 或保留原配置上下文；不要把测试环境路径错误误判成线上配置故障。

参考：[Nginx URI 转发](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)、[return 和 rewrite](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html)。

## 交付与回退

核对正式首页、语言入口、一个列表/详情、图片、脚本、样式、版本与 robots；校验原预览跳转及查询参数。必要时做真实浏览器检查并保存实际截图，不用生成图冒充验收。

交付两种回退的区别：静态内容版本回退通常恢复同一目录的干净静态版本；入口配置回退恢复本次代理备份，可能回到“只有预览网址可用”的状态。都不能为了回退内容而重新公开失修 PHP 程序。

维护说明明确写出当前正式域名、物理上传目录、工具启动方式、连接测试 → 生成发布预览 → 上传的顺序、完整编辑备份位置、索引设置及语言覆盖情况。历史试用说明不能继续指挥用户上传到当前路由不用的目录。
