# 资料评估与恢复

用于旧程序失修、因漏洞停站、源码与服务器备份版本不同，或中英文资料不完整的项目。

## 是否适合静态化

| 功能 | 常见处理 |
| --- | --- |
| 公司介绍、新闻、产品、案例、下载 | 结构化内容 + 静态页面，保留稳定 ID、图片与附件 |
| 站内产品搜索、分类、图片切换 | 小型公开 JSON/索引和浏览器脚本 |
| 后台改图改文 | 本地编辑 → 预览 → 生成 → 发布 |
| 留言、询盘、验证码、上传 | 明确接收端；沿用安全后端、另建小型 API 或经用户选择的替代方式 |
| 登录、付款、订单、会员和实时库存 | 单独评估和保留后端；不要当静态文件迁移 |

静态化减少公开动态程序的暴露面，但不自动修复主机、账号或代理配置。先根据业务和现有资源选择方案，不默认要求换主机或购买服务。

## 原始备份只读，先复制再处理

原始源码、数据库备份、网页压缩包和媒体是恢复依据，按只读资料保留。元数据盘点、计算摘要和复制可以读取原件；以下解压、SQL 解析、清洗、恢复和改造都使用独立副本。

1. 记录原始路径，在所有原件目录之外选择新的私有工作区；工作区和输出目录也不能经符号链接、Windows 目录联接或其他重解析点指回原件。先估算复制、解压与生成结果所需空间，空间不足时说明缺口并停止，不在原件上继续。
2. 在原件目录之外保存来源清单。普通文件和压缩包记录大小与 SHA256；源码或媒体目录记录相对路径、大小和文件内容摘要，链接单独列出、不自动遍历。不要为“保护备份”擅自修改原件权限或文件属性。
3. 将每份来源独立复制到本次工作区，保留来源与副本的对应关系。不使用硬链接、符号链接或目录联接伪装副本；链接和特殊文件先单独核对。目标已存在时选择新的工作目录，不合并覆盖已有工作成果。
4. 开始处理前核对副本与原件清单一致。复制失败、内容不一致或检查未完成时停止，不把部分副本当作完整备份。随后从副本解压到工作区的新目录、恢复到隔离数据库，并只修改工作文件；静态站、日志和报告写到新输出目录。
5. 完成后重新核对原件清单和摘要，报告实际核对范围及差异。若原件发生变化，停止继续发布并保留现场，先查明来源。失败清理只针对本次工作区，不能删除或覆盖原始备份。

建议布局为并列的 `originals/`、`work/run-ID/sources/`、`work/run-ID/extracted/`、`private/` 与 `public/`；现有原件保持原位，无须为了符合示例而移动。来源清单保存在 `private/`，公开目录仅保存经筛选的发布文件。是否只读是使用规则，不能仅凭文件夹名断言已实现隔离。

## 先记录来源，后抽取内容

来源表应包括：原始文件/目录、对应工作副本、获取位置、备份日期、体积、校验值（计算过才写）、复制核对结果、语言、内容范围、可信度和与其他版本的差异。

- 分别寻找源码、SQL/SQL.GZ、网页 ZIP、Uploads/附件、现有静态发布记录；不要把目录名字里的日期当作内容新旧的唯一证据。
- 代码里的硬编码演示数据常落后于 SQL；网页备份可能包含更新的图片或正文。选择每类数据的权威来源并保留映射依据。
- 多份 SQL 比较规范化数据和更新时间，而非只比较压缩文件 SHA。表缺失、空表、字符集、表前缀和字段名变化都要单独记录。
- 英文数据单独核对；缺表时区分“恢复原英文”和“从中文生成新译文”。不要用中文内容冒充原英文。
- SQL 同时可能包含账号、私钥、用户表和邮件配置。只抽取拟公开的业务字段，不在日志里打印配置值或用户资料。

`inventory_sources.py` 只盘点目录和 ZIP 条目，不解压。SQL.GZ 按压缩数据文件登记；它不会展开 gzip、解析 SQL 或为任意 ZIP 提供内存隔离。大型 ZIP 会先由标准库读取中央目录，条目上限约束的是报告范围。

通过 SSH 读取 Windows 资料时，先核对实际目录、运行时版本和字符编码。大段 PowerShell 放到受控私有脚本文件，核对哈希后调用，避免超长 `EncodedCommand`；不要为执行一次迁移脚本改全局执行策略。只读检查与后续脚本写入分清，遵守当次授权范围。

## 不运行旧系统也能恢复的部分

优先把工作副本中的 PHP/ASP 模板、SQL、HTML 和配置当数据读取。不要为了看首页就把失陷风险不明的程序对外启动，也不要把备份直接导入生产数据库。

SQL 抽取要覆盖当前转储实际使用的语法：显式列名、扩展 INSERT、多行字符串、转义引号、反斜线、NULL、编码和数字类型。用带这些情况的小样本验证解析器；遇到未支持表达式时报告，不静默丢行。不把临时写的正则解析器包装成通用 SQL 解释器。

确需数据库重建时，使用经授权的隔离环境和数据范围，检查触发器、事件、存储过程、UDF 与权限语句。恢复和查询不能触及生产库。需要旧运行时渲染时先明确隔离和网络边界，不默认允许旧程序接触原凭据。

## 内容及资源映射

- 记录菜单、栏目、分类、公开/草稿状态、产品稳定 ID、正文、图片、下载与联系信息的映射。产品重名不等于重复记录。
- 图片可能在新网页备份中，数据库只存附件 ID。核对 ID → 路径、大小写、实际文件和正文内相对路径；保留缺失列表。
- ZIP 中绝对路径、`..`、重复条目和符号链接先列出；若要解压，读取工作副本并使用新的解压目录，另用安全路径约束、资源预算和明确选择，不能直接 `extractall` 到原件、项目或公开目录。
- core dump、日志、缓存通常是体积大头；先用元数据分组。生成缓存也可能是缺失正文的线索，不因名称像缓存就直接删除。
- 保留旧 URL → 新 URL 的来源映射，供后续重定向使用；不要为凑页面数量凭空补内容。

## 维护性和外观

先观察原导航、颜色、字号、版心、图片比例与移动端需求。默认保留已有品牌及内容关系，重建干净模板；重设计是另一个选择。商标、证书、产品图和下载材料优先复用权威文件，不自行替换成生成图片。

恢复结果应能回答：当前公开了多少条产品和文章、哪些资料缺失、每种语言来自哪里、哪些动态功能已经分离，以及哪个完整资料文件将作为后续编辑起点。
