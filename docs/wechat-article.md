# 我把停用的老官网改成静态站并整理成了 Codex Skill

最近，我和 Codex 一起改造了一份因安全问题停用的企业官网。

它还在用 PHP 5.5 和 MySQL 5.1，放在一台 1 核 1G 的云虚拟主机上。平时只能通过 FTP 上传文件，主机的启动和关闭都在网页控制台操作。

网站承担的工作很普通：介绍公司、展示产品、发布新闻，提供中英文内容。产品资料和图片还要用，旧后台却已经成了恢复运行的障碍。

这次改造完成后，我把资料恢复、内容维护和上线过程中遇到的问题整理成了一份 Codex Skill，叫 **legacy-site-to-static，老官网静态化改造**。遇到类似网站时，可以让 Codex 沿着这套流程评估和实施。

## 先判断官网还需要哪些功能

一开始，我想知道能否升级 PHP、给旧程序打补丁，然后把网站重新打开。

检查后发现，问题涉及旧框架、编辑器、上传入口和配置等多个部分。仅仅更换 PHP 版本，无法说明整套旧程序已经可以放心恢复。

而这份官网的主要内容是公司介绍和产品目录。访客浏览页面时，并不需要服务器每次查询数据库、运行 PHP，再拼出相同的内容。

于是我们采用了静态化方案：在本地整理资料，生成 HTML、CSS、JavaScript 和图片，再把生成结果上传到主机。原有主机继续承担网页访问，旧程序则归档到非公开位置。

对于这类展示站，维护流程由此变得清楚了：

**本地修改内容 → 生成预览 → 核对页面 → 发布静态文件。**

## 内容恢复要同时查看几份备份

真正动手后，最先遇到的是资料问题。

本地源码、从服务器下载的数据库、网页文件备份，各自保存着不同部分的信息。源码能帮助理解页面结构，最新数据库可能保存更新的产品介绍，图片和下载资料又可能只在网页备份里。

如果只用源码里的初始数据，做出来的页面即使能打开，也可能丢掉后来维护的内容。

英文版还遇到了另一种情况：备份里缺少旧代码需要的一张内容表。对此只能核对其他资料，或重新准备译文，不能把缺失的原英文内容说成已经恢复。

所以，这份 skill 的第一步是建立资料来源表：正文以哪份数据库为准，图片来自哪里，哪些资料缺失，哪些结论还需要确认。之后再生成页面、逐项核对。

## 静态官网以后怎么加产品

这是我最关心的问题。官网重开之后，产品图片和介绍还会继续更新。

这次我们做了一套本地管理工具。在自己的电脑浏览器里编辑产品、选择图片、预览页面，确认后生成新版本，再通过 FTP 发布。

新增图片会在生成时进入发布目录，页面引用与图片一起上传。日常维护不必再手工寻找每张图片对应的远程位置。

英文内容也接入了翻译服务。中文修改后可以生成英文译稿，检查型号、参数和措辞，再人工确认。中文原文变化时，还要重新判断旧译文是否适用。

这里有一个容易忽略的细节：**完整编辑资料和公开网站文件要分别保存。** 待审核译稿、编辑状态等信息不应直接公开；继续维护时，则需要最近的完整编辑备份。

这些能力已经在这次项目里实现。通用 skill 会指导 Codex 根据当前网站制作合适的管理和发布工具，仓库本身没有附带一套所有网站都能直接安装的后台。

## 上传完成之后还要验证访问链路

上线时，我们遇到过一个很直观的问题：FTP 显示发布完成，云虚拟主机也已经启动，访问域名仍然返回 503。

最后查明，请求会先经过另一台服务器上的 Nginx，那里保留着维护期间的 503 拦截规则。源站文件已经就绪，域名入口仍被挡住。

这件事让我意识到，上线需要沿着真实访问链路检查：域名解析指向哪里，前面有没有代理，代理连接哪个源站，源站最终读取哪个目录。

旧程序归档和目录权限也要核对。把旧 PHP 移到网站目录里的另一个文件夹，仍可能留下访问入口；普通文件权限设置也不能直接当作禁止 PHP 执行。

skill 因此要求在切换前准备备份和回退方法，切换后核对正式网址、内容版本、图片和关键页面。发布目录即使叫作 preview，一旦已经承载正式域名，后续上传也会直接更新官网。

## 我把这些步骤整理进了 skill

Skill 可以理解为交给 Codex 的一套可复用工作流程。它说明什么时候适用、如何处理资料不全、按什么顺序实施，以及交付时需要说明哪些事实。

这份 skill 覆盖资料评估、静态页面生成、本地维护、多语言审核、FTP 发布、入口切换和回退，并附带三个只读工具：

- 来源盘点工具，查看目录和 ZIP 的文件分布与路径异常。
- 发布检查工具，核对本地资源引用、路径大小写、缺页及项目声明的内容规则。
- HTTP 检查工具，对明确指定的网址检查响应，帮助区分跳转、拦截和源站状态。

例如，产品数据里有一条记录，生成结果却没有对应详情页，就应该被发现。上一版有已确认英文内容，新版本数量意外下降，也应该先查资料来源。

这些脚本已经用合成资料做过回归检查，也做过独立的离线案例试跑。实际项目仍要核对正文和图片，并在浏览器里检查页面与交互。

## 哪些网站适合尝试

公司介绍、产品目录、新闻、案例和下载中心，都可以先评估静态化。原有主机只要支持静态文件访问，也有机会继续使用。

有登录、下单、支付、会员资料或实时库存的网站，需要保留或重建相应后端。联系表单同样需要真实的接收服务。

静态化减少了公开服务端程序的攻击面，主机、账号、代理和本地工具仍要维护。它适合解决展示内容的恢复与持续更新，具体方案要根据网站的实际业务决定。

## 从一次只读评估开始

我把通用 skill 和检查脚本放到了 GitHub，移除了原公司的源码、数据和部署信息：

https://github.com/reinmj/skills/tree/main/skills/legacy-site-to-static

安装时，在 Codex 里输入：

```text
使用 $skill-installer，从 https://github.com/reinmj/skills
安装 skills/legacy-site-to-static。
```

然后提供资料位置：

```text
用 $legacy-site-to-static 评估这个老官网。
源码在……，数据库备份在……，图片和网页备份在……。
先只读评估，再制作本地静态版本，保留现有内容和风格。
```

安装与调用方式可参考 [OpenAI 官方 Skills 文档](https://learn.chatgpt.com/docs/build-skills)。

如果你手里也有一份多年未维护的企业官网，可以先拿备份做一次评估：需要保留哪些业务，内容是否齐全，静态化后由谁维护。把这些问题弄清楚，再决定怎样重开网站。
